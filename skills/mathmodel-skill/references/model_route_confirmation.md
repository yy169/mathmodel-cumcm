# 主模型路线人工确认门禁

在 Stage 3 候选模型、文献证据和初步决策矩阵完成后，正式锁定主模型、编写主体求解代码
或开始论文前使用。目标是让用户在错误路线成本扩大前检查题目理解和证据方向。

## 1. 默认必须暂停

生成候选比较后，`decision_log.stages.3.human_model_checkpoint.status` 默认为 `pending`。
在用户明确回复批准、选择替代路线或提出修改前，不得：

- 把推荐候选写入最终 `selected_per_subproblem`；
- 进入 Stage 4 的最终假设与符号冻结；
- 开始 Stage 5 主体求解；
- 写摘要或论文正文；
- 把候选创新称为最终创新。

允许继续的只有低成本信息整理、文献补充和候选路线澄清。

## 2. 必须向用户汇报的内容

生成 `reports/model_route_checkpoint.md`，并在对话中主动报告：

1. **题目深层理解**：每个 Qi 真正要解决的矛盾、输入、输出和约束；
2. **数据条件**：附件规模、缺失、异常、可用标签和不能从文献补出的信息；
3. **知识与文献缺口**：哪些已经解决，哪些仍为 `conditional`；
4. **检索过程**：题面触发词、中英文关键词、数据库和高质量文献短名单链接；
5. **候选模型**：每个 Qi 至少列出所有真实合理候选，不凑数量；
6. **推荐路线**：为什么更匹配题目、数据和时间预算；
7. **否决路线**：为什么不选，以及是否可能作为基线或消融；
8. **预期创新**：相对什么基线改变了什么，准备如何验证；
9. **求解计划**：代码、求解器、复杂度、初始化和失败回退；
10. **验证计划**：基线、消融、稳健性、负面结果和图表证据；
11. **主要风险**：哪些假设或缺失证据可能改变路线；
12. **需要用户决定的事项**：推荐选项和可替代选项。

## 3. 推荐确认表

| Qi | 候选模型 | 适配证据 | 文献证据 | 数据要求 | 验证方式 | 风险 | 建议 |
|---|---|---|---|---|---|---|---|

最后只询问必要决策，不把几十个小问题一次抛给用户。推荐格式：

```text
我建议采用：Q1=...，Q2=...，Q3=...
需要你确认：
1. 是否批准该主路线？
2. 是否保留候选 B 作为基线/消融？
3. 是否有必须纳入的行业标准、方法或限制？
```

## 4. 用户反馈后的状态

写入：

```json
{
  "status": "pending | approved | revision_requested",
  "report_path": "reports/model_route_checkpoint.md",
  "recommended_route": {},
  "alternatives": {},
  "user_decision": "",
  "approved_at": null,
  "required_changes": [],
  "invariants_after_approval": []
}
```

- `approved`：按确认路线继续，并把模型、基线和验证计划列为当前不变量；
- `revision_requested`：只修改用户指出或证据受影响的候选，重新汇报差异；
- `pending`：不得越过门禁。

用户后续提供的新文献或附件若足以改变路线，状态重新设为 `pending`，执行定向复核，不得
静默更换模型。

## 5. 何时不需要重复确认

同一任务、同一题面、同一数据和同一权威结果源下，用户已经批准且没有新证据改变路线时，
不重复询问。语言润色、排版和不改变模型的图表重绘不会重新触发。
